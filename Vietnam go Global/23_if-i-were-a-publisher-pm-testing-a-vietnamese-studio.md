# If I Were A Publisher PM Testing A Vietnamese Studio

Testing a Studio is not the same as delegating a task.

That sounds obvious, but a lot of bad deals begin because the Publisher thinks they are testing a Studio while actually just giving them work.

If I were a Publisher PM, I would design the test around learning speed, not just production speed.

The 6-week logic would look like this:

### Week 0
- Define scope;
- Define what success means;
- Define what failure means;
- Define who owns what.

### Week 1
- Build the core;
- Instrument the right events;
- Make sure the output is readable.

### Week 2
- Check marketability;
- Check clarity;
- Check whether the concept can be understood fast.

### Week 3-4
- Read Retention;
- Inspect fail points;
- Review economy and onboarding issues.

### Week 5
- Decide iterate / kill / scale.

### Week 6
- Write the learning;
- Decide the next bet.

The formula is:

> 6-week test = scope -> build -> instrument -> marketability -> Retention read -> decision

The Studio is not being tested only on the prototype.
It is being tested on how it learns.

That matters in Vietnam because the market has many capable teams. The real question is not “Can they make something?” It is “Can they make a useful decision from what they made?”

If I were a Publisher, I would want:

- A clean hypothesis;
- A strong test design;
- A readable event map;
- A clear kill criterion;
- A written post-test summary.

If the Studio cannot work in that format, then the partnership is not ready yet.

In the next 2-4 years, the best Publisher PMs will be the ones who know how to test Studio maturity, not just output quality.

I would also avoid testing too many things at once.

A common Publisher mistake is to give a vague brief, expect a strong prototype, then judge the Studio harshly when the result misses a hidden expectation.

That does not reveal talent.
It reveals that both sides entered the test with different mental models.

For a first collaboration, the test should be narrow enough that the Publisher can understand the Studio’s working behavior.

I would not ask:

> Can you make a hybrid puzzle hit?

That question is too large.

I would ask:

> Can you turn this mechanic and this player promise into a playable test with clean scope, readable UX, basic event tracking, and a written learning summary in two weeks?

That question is useful.

It reveals production speed.
It reveals design judgment.
It reveals technical discipline.
It reveals communication maturity.
It reveals whether the team understands why the project exists.

The first test should create a map of the team.

I would score the Studio across six dimensions:

- **Execution Speed**: how quickly they produce a playable build.
- **Design Reasoning**: whether they can explain why a mechanic should work.
- **Data Readiness**: whether events and test goals are understood.
- **Communication Hygiene**: whether questions, notes, and risks are written clearly.
- **Production Judgment**: whether they know what to cut.
- **Learning Behavior**: whether they improve after feedback.

This score is more useful than asking whether the first prototype is “good.”

Many first prototypes are rough.
That is normal.

But rough and thoughtful is very different from rough and confused.

If the Studio is rough but thoughtful, I would invest more time.
If the Studio is polished but unable to explain decisions, I would be careful.

For Vietnamese teams, this also creates a clear path to win trust.

You do not need to pretend that you already know everything.
You need to show that you can learn correctly.

Before the first meeting, send:

- The questions you need answered;
- The assumptions you are making;
- The risks you already see;
- The smallest test scope you recommend;
- The decisions you need from the Publisher.

After the meeting, send:

- What was decided;
- What was not decided;
- Who owns each next step;
- What risk remains;
- What will be delivered next;
- When the next decision happens.

This single habit can separate a serious Studio from a passive vendor.

It also reduces cultural misunderstanding.

Vietnamese teams may avoid pushing back directly in a call. Western PMs may interpret silence as agreement. Both sides may leave the meeting thinking everything is clear. Two weeks later, the build reveals that the agreement was not actually shared.

Written confirmation fixes much of this.

Not perfectly, but enough to reduce waste.

If I were a Publisher PM, I would create one shared page for each test:

- Brief;
- Assumptions;
- Scope;
- Milestones;
- Events;
- Risks;
- Decisions;
- Postmortem.

Then I would watch whether the Studio uses it actively.

That behavior tells me more than a sales deck.

In the next 2-4 years, Publishers looking at Vietnam should not only ask which Studio is cheap or fast. They should ask which Studio can become a repeatable operating partner.

The first project is not only a prototype.

It is a test of how the team thinks when the answer is not obvious.

That means I would never evaluate the Studio only by one prototype.

I would also ask whether they became easier to work with after the first round.
That is the real sign of a partner worth building with.

If I had to score the Studio on a simple 1-to-5 scale, I would use:

- Execution Speed;
- Design Reasoning;
- Data Readiness;
- Communication Hygiene;
- Production Judgment;
- Learning Behavior.

That is the kind of scoreboard the infographic should mirror.
