# Team Thiếu Data

If you do not have Data, you are probably optimizing by feeling.

That is the uncomfortable truth.

Many game teams have output but weak instrumentation.
They can ship.
They cannot always explain what the ship meant.

That is why Data hygiene matters.

The minimum structure should include:

- Event map;
- Cohort;
- Funnel;
- Decision log;
- Postmortem;
- One source of truth.

The formula is:

> Data work = instrumentation + interpretation + decision

Logging events is not enough.
You must also read them.
And after reading, you must decide.

That is where many teams struggle.

They fix by feeling.
They revise by instinct.
They cannot distinguish:

- Product signal;
- Creative signal;
- Bait signal;
- Retention signal;
- Economy signal.

AI can help a lot here:

- Summarize reports;
- Generate event checklists;
- Compare test variants;
- Explain patterns in plain language.

But AI only helps if the team has basic discipline already.

If I were a PM, I would ask: which event proves our hypothesis?
If I were a Designer, I would look at fail Data before changing the level.
If I were a Founder, I would want a simple way to see where the product is leaking.

In the next 2-4 years, teams with basic Data hygiene will move much faster than teams that only trust instinct.

No Data, no real learning.

A team thiếu Data usually does not fail in one dramatic moment.

It fails through small guesses repeated for too long.

The Designer guesses why players quit.
The Developer guesses which bug matters most.
The PM guesses whether the build is ready.
The Founder guesses which game deserves more time.
The Publisher guesses whether the Studio understood the test.

Some guessing is normal.

But if every important decision is guesswork, the team is not operating. It is gambling with effort.

A young Vietnam Studio does not need a perfect analytics stack immediately.

It needs a minimum Data habit.

Start with:

- D1 Retention;
- D7 Retention if the test lives long enough;
- First-session length;
- Level fail rate;
- Level retry rate;
- Tutorial completion;
- Ad engagement;
- IAP funnel if relevant;
- Crash rate;
- Source of traffic.

Then connect every metric to a decision.

Do not collect Data because it looks professional.
Collect Data because it changes action.

Examples:

- If tutorial completion is low, fix onboarding before adding content.
- If level fail rate is high but retry is also high, pressure may be useful.
- If fail rate is high and retry is low, trust may be broken.
- If CPI is bad but gameplay metrics are good, creative or market promise may be the issue.
- If D1 is weak, do not talk too early about long-term Live Ops.

AI can help non-Data people understand Data.

Prompt:

> Explain these game metrics for a Game Designer. Separate facts, possible interpretations, and recommended next questions. Do not overclaim.

That last line matters: do not overclaim.

Data does not automatically tell the truth.
It gives signals.

The team still needs context, observation, and judgment.

For young Vietnamese talent, learning basic Data language is now career protection.

A Designer who can read Retention is stronger.
A PM who can connect Data to decisions is stronger.
A Developer who understands event quality is stronger.
A Founder who knows the limits of the Data is stronger.

In the next 2-4 years, “I am not a Data person” will become a weaker excuse.

You do not need to become a Data Scientist.

But you do need to stop making important game decisions in the dark.

If you want the minimum discipline, start with one dashboard and one question.

One dashboard:

- Retention;
- Playtime;
- Fail rate;
- Retry rate;
- Monetization signal;
- Crash rate.

One question:

> What decision does this metric support?

That question prevents vanity reporting.

It also stops the team from pretending that more charts equal more insight.

If the metric does not change a decision, it is not yet useful enough.

That is the standard I would use in a young Studio.

If I were turning this into a compact board, I would show:

Metric -> Decision -> Action

That simple sequence makes the problem visible immediately.
